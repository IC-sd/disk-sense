# 垃圾清理：开源研究与能力改进

研究日期：2026-10-23；应用发现与验证补充于 2026-10-24。目标是让规则发现、扫描计量、候选选择和执行结果可以核对，并减少重复文件系统访问。本轮没有执行用户文件清理。

## 已补的缺口

### 1. 重叠目录导致重复计量

此前同一规则同时包含父目录和子目录时，会分别入队，造成候选数量、占用及“近期保留”重复计数。现在按 Windows 规范路径去重配置根，并在成功打开目录后登记实际目录路径，同一规则共享遍历。计量和候选收集也按实际文件路径去重。

文件会先通过类型、实际路径和规则根边界检查，再进入占用或保留时间统计。不同硬链接名称保留为不同目录项，不用 inode 合并删除对象；显示的逻辑字节数不代表实际可释放簇数。

### 2. 失败与空结果难以区分

普通扫描返回 `coverage`：

| 状态 | 含义 |
| --- | --- |
| `complete` | 已完成本规则解析出来的目录遍历，按规则跳过链接、不匹配项、保留期内文件等 |
| `partial` | 已读到部分目录，但存在读取错误、文件变化或扫描资源限制 |
| `unavailable` | 没有成功打开目录且存在错误或资源限制；系统汇总也可能整体不可读取 |
| `not-found` | 未发现规则位置，或所有解析出来的位置均不存在 |
| `excluded` | 未读取到目录，至少一个根被用户排除，其他根不存在或同样被排除 |

`ENOENT` / `ENOTDIR` 出现在初始规则根时属于位置不存在；若出现在扫描已发现的子目录或文件上，则作为扫描期间变化记录。其他错误保留阶段、路径和代码。每条规则最多返回 20 条诊断样本，同时保留总错误数和省略数量，避免错误列表无界增长。

界面展示状态、问题路径、可读原因，以及缺失/排除位置数量。完全不可读的规则显示“未能读取”，不显示成成功扫描到 `0 B`。部分结果仍可核对，原有进程、风险、排除与身份校验继续生效。系统回收站汇总也标记部分卷读取失败。

### 3. 不匹配文件较多时进度和取消不及时

进度上报和事件循环让出移动到每 200 个已访问目录项的位置，放在名称过滤、排除和目录分支之前。即使目录里全部是不匹配文件，也能更新进度和响应取消。文件系统中单次尚未返回的调用仍不能被强制取消。

### 4. 跨规则候选可能重复进入清理计划

前端按实际文件路径生成唯一的可处理文件集合、数量、大小和选中集合。主进程在整个分批任务中共享已成功处理路径集合，同一路径的不同候选 ID 不会再次执行回收站操作，也不会重复累计成功字节。失败或被安全条件阻止的候选不会占用成功路径集合，其他有效候选仍可重试。输入仍只能引用主进程登记的候选 ID。

所有规则的“已知占用”仍是规则统计与只读汇总相加，可能交叠，界面明确标注；它不能用于声称已经全局去重或可立即释放。移入回收站的记录继续保持 `reclaimedBytes = 0`。

### 5. 位置解析和外部调用

每次扫描只解析一次动态根目录，返回的 `locations` 与实际扫描相同。无进程限制的规则不再启动 `tasklist`；需要进程检查时，与扫描并行执行。重扫开始即移除对应旧结果；整轮扫描清空前次结果与选择，避免失败后仍显示旧的成功结果。Windows 本地应用数据位置优先使用 `LOCALAPPDATA`，再回退到用户目录。

### 6. 应用发现阶段也报告覆盖情况

2026-10-24 将浏览器 Profile、标准 Electron 缓存、Firefox、JetBrains 和按名称查找应用缓存的逻辑提取到 `desktop/cleanup-discovery.cjs`。每次规则扫描显式传入独立的发现上下文，避免并发规则共享错误状态。

- 用可区分错误的目录状态检查替代 `existsSync`，权限失败不会再被当成不存在。初始缺失位置属于正常发现结果；已核实位置在读取时消失则属于发现错误。
- 返回发现阶段的目录读取数、检查项数、不存在位置数、用户排除位置数、跳过链接数和预算耗尽标志；诊断与文件扫描共用每规则最多 20 条样本的上限。
- 按名称发现使用 `opendir` 流式枚举。每个应用根保留一份目录预算，默认总目录预算 2,000、扫描规则可指定最大深度；整个发现上下文另有 10,000 个检查项上限，并纳入本规则总扫描时间上限。深度、目录数、检查项数和时间耗尽均有明确诊断。
- 发现目录前应用用户排除项，跳过符号链接与 junction；每 200 个检查项报告发现进度，并检查取消。文件扫描阶段另行校验实际根目录、文件路径和身份。
- 已发现的有效缓存仍可进入后续安全校验，其他位置发现失败时返回部分结果。界面分别展示应用位置发现与文件扫描情况，不把达到深度上限描述成“没有垃圾”。

同步 Profile 枚举中的单次系统调用仍不可抢占，也可能先分配完整目录列表；应用发现覆盖的是内置默认位置，不代表所有便携版和自定义配置位置。

## 验证

- `tests/cleanup-scan-quality.test.ts` 新增 29 项行为测试，覆盖重叠计量、保留文件、硬链接名称、读取故障、有界诊断、取消、资源限制、执行去重，以及发现阶段权限错误、位置消失、预算分配、排除项、链接、并发上下文隔离与动态解析异常。
- 全量测试：40 个文件、301 项通过。类型检查、生产构建和 41 个桌面模块语法检查通过。
- 真实 Electron 使用隔离用户目录和自建样本检查完成、缺失、不可读与部分扫描四种状态，包括应用发现达到深度上限时仍保留有效缓存，以及确认后才执行的界面流程。没有执行删除、回收站移动或系统维护。
- 可重复运行 `node scripts/benchmark-cleanup-scan.cjs`，结果保存在 [cleanup-scan-benchmark.json](cleanup-scan-benchmark.json)。640 文件、3 个重叠根：独立逐根参考扫描累计计数 1,540，合并后 640；候选由重复的 790 变为唯一的 340；目录打开 6 次变为 3 次。参考组使用同一个扫描器逐根运行，不是历史程序版本的实测对比；耗时受到顺序和文件系统缓存影响。
- 最终桌面检查和截图入口见 [cleanup-validation.json](cleanup-validation.json)。

## 后续能力缺口与采用顺序

1. **规则声明与版本管理。** 借鉴 CleanerML 的 schema 思路，将路径策略、匹配器、保留期、风险、应用进程、来源和版本拆成可校验数据；执行动作仍由主进程白名单控制。需要版本迁移、无效规则拒绝、每个应用的正反样本，以及更新包来源校验。
2. **应用发现的完整性。** 浏览器与桌面应用缓存发现已报告读取错误和预算耗尽；仍需支持自定义浏览器资料目录、便携版、更多应用版本及安装/配置来源。包管理器配置发现仍由 `tool-cache-locations.cjs` 单独负责，其配置解析警告尚未接入此报告。`complete` 不代表应用在任意位置保存的所有缓存都已发现。
3. **跨规则共享扫描。** 本轮只共享同一规则内的重叠遍历。不同规则共享父目录、匹配器分派和占用账本，需要单独的扫描会话；应同时保留每个规则的风险、排除条件、保留期和来源。不能用全局简单 Set 丢掉另一规则的安全条件。
4. **更准确的空间收益。** 需区分逻辑大小、实际分配大小、硬链接、稀疏文件、压缩文件与云占位文件，并明确回收站占用。当前不声称“发现占用 = 释放空间”。
5. **更多应用规则与跨版本验证。** 仍为原有 28 条内置规则。本轮没有通过放宽目录匹配增加候选量。新增规则应有软件版本、数据用途、可重建依据和真实 Windows 样本；包管理器存储继续由原生工具管理。
6. **执行与恢复能力。** 当前逐文件调用 Electron 回收站接口、逐文件记录结果。原生批处理、操作期间崩溃恢复和跨卷行为需要专门设计，并在真实 Windows 环境中验证。没有引入永久删除、注册表清理或外部清理脚本执行。
